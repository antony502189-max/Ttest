# AI-поиск: эксплуатационные и продуктовые правила v1

Дата: 2026-11-01. Область: закрытый первый текстовый стенд, пункт 6.
Публичный выпуск, производственный runtime, голос и доставка уведомлений —
отдельные этапы. Этот документ задаёт правила; фактические проверки перечислены
в [отчёте](../../reports/AI_OPERATING_POLICY_20261101.md).

## 1. Данные и внешние сервисы

- Исходная фраза живёт только в памяти запроса и вкладки. Не сохранять её в БД,
  логах, traces, error reports, localStorage/sessionStorage или файлах.
- В БД разрешены только типизированные allowlist-критерии, версии и минимальные
  UUID/хеши для ownership, квоты и повторов. Они остаются приватными данными.
- Модель не получает контакты, имя, IP, cookies, токены, subject/session/result ID,
  платёжные данные, биографии, медицинские сведения, полные HTML или URL источника.
- Сейчас внешний intent разрешён только отдельной закрытой оценке с точным
  `SyntheticCorpusGate`: утверждённые синтетические фразы и критерии. Произвольный
  пользовательский текст этот gate не пропускает. Ключ сам по себе AI не включает.
- Для реальных пользователей сначала подтвердить для конкретного provider account
  цель, разрешённые поля, место обработки, отсутствие обучения, сроки хранения и
  удаления, ответственного; внедрить проверяемую минимизацию. Пока этого нет,
  real-user outbound запрещён. Regex не считается доказательством минимизации.
- Разрешение на ограниченный Flatio pilot и расходы отдельного intent eval не
  расширяется этим документом. Нельзя отправлять объявления в intent-модель или
  сбрасывать накопленный бюджет повторной оценки.
- Наблюдаемость: только фиксированные коды, длительности и агрегатные счётчики.
  Не включать приватный текст, criteria/evidence, ключи и SQL/DSN в сообщения ошибок.

## 2. Хранение и удаление

| Данные | Срок и действие |
| --- | --- |
| Raw text/provider body | Память текущей операции; серверный execution deadline 15 с, HTTP 20 с |
| Черновик | Память вкладки; очистка после 15 минут без редактирования, кроме неопределённой операции |
| Неопределённая операция в UI | Только память текущей вкладки; точный payload нужен для безопасного повтора; reload его не сохраняет |
| Continuation locator | Только session/result UUID в sessionStorage текущей вкладки; повторная авторизация и проверка TTL на сервере |
| Диалог и результаты | Доступ до 24 ч бездействия, абсолютный предел 7 суток от создания; reset/close прекращает доступ |
| Приватные criteria/result intent | Физическая очистка после 24 ч от окончания доступа, пакетами до 1000 строк |
| Неиспользованный seed без команд/операций | Очистка после 1 ч |
| Квитанции операций/команд и usage days | 30 суток; не удалять защиту от повтора живого диалога; команда сохраняет минимальную закрытую FK-оболочку без criteria |
| Prepared proof/metadata | 24 ч от подготовки; очистка отдельно от freshness источника |
| Непривязанные AI evidence/facts/batches и завершённые старые jobs/events | 7 суток, с сохранением активной generation и ссылочной целостности |
| AI-копии удалённых/непубличных объявлений и владельцев | Немедленное исключение из выдачи; физическая очистка ограниченными проходами |
| Независимые deletion intents | Зашифрованные UUID и время: 31 сутки; после успешного replay очистка старых записей |
| Backup с приватным AI состоянием | Допустимый горизонт восстановления ≤30 суток; не возвращать трафик до replay независимого deletion journal |

Expiry — запрет доступа, а не физическое удаление. В Compose работает отдельный
maintenance-процесс с restart policy: recovery каждые 5 с, retention ежечасно;
при backlog — следующие ограниченные проходы через 5 с. Deadline прохода 15 с,
SQL statement 3 с / lock 1 с, пул 1. Ошибка не запускает provider и не списывает
квоту. Мониторинг отставания и проверка production supervisor относятся к выпуску.

Удаление аккаунта и административное удаление очищают приватные AI sessions,
results, requests, квоту и saved snapshots под общим порядком блокировок.
Новый AI-диалог удалённого аккаунта запрещён; reset/удаление истории квоту не сбрасывают.
Принятое намерение удаления сначала записывается в независимый журнал: rollback
или потерянный ответ не отменяют его, повторный replay завершает удаление.

Журнал хранится вне PostgreSQL backup, в отдельном постоянном volume, AES-GCM с
независимым ключом. Подписанная цепочка и привязка journal UUID в БД отвергают
повреждённый, отсутствующий или подменённый пустым журнал. Инициализация — явная
команда; автоматически заменять утраченный журнал нельзя. Синтетический ключ в
lab Compose использовать только в этом стенде.

До restore: изолировать восстановленную БД, получить свежий подписанный checkpoint
из авторитетного независимого журнала и выполнить:

```
python -m app.commands.ai_erasure_journal checkpoint --output <checkpoint.json>
python -m app.commands.ai_erasure_journal restore --checkpoint <checkpoint.json> --backup-created-at <trusted-UTC-timestamp>
```

Для команд явно задать `AI_ERASURE_JOURNAL_PATH`, `AI_ERASURE_JOURNAL_KEY`
(base64, 32 байта), для restore — `AI_RESTORE_DATABASE_URL`. Timestamp брать из
доверенного backup manifest: произвольный аргумент оператора не доказывает возраст
архива. Checkpoint действителен 5 минут; изменение журнала требует нового прохода.
Нет журнала/ключа, неверная привязка, старый backup или ошибка replay — трафик
остаётся закрытым. Шифрование backup и его удаление в пределах 30 суток должны
быть подтверждены в конкретном окружении перед реальными данными.

## 3. Свежесть и недоступность источников

Proof v2 подтверждает соответствие сохранённому состоянию. Время пересборки
proof, extraction или общего import run не доказывает недавнюю проверку источника.
Публичная карточка требует одновременно eligibility, актуальный proof и отдельный
source freshness guard до count/order/LIMIT, включая map и повторную выдачу.

Профиль первого стенда консервативно разрешает внешние active записи с
`last_success_at` не в будущем и возрастом ≤24 ч. Все связанные источники,
которые могут влиять на подтверждение, должны пройти guard; missing timestamp,
unknown/unavailable status исключают карточку. Граница 24 ч включительна.
Записи native без поддерживаемой evidence-цепочки AI не подтверждает. Поиск по
конкретным датам и более короткие holiday/availability TTL требуют отдельного
профиля и проверки источника; текущий стенд не обещает наличие для бронирования.

Пересборка proof не обновляет `last_success_at`. Ошибка/403/429/CAPTCHA/timeout
не являются успешной проверкой и не продлевают TTL. Удаление, remap, изменение
identity/content, конфликт или pending generation исключают данные по прежним
v2 current-input guards. В пользовательском поиске нет live crawl/model на карточку.
Для синтетического lab launcher явно запускает `lab.recheck_synthetic`: проверяет
точную fixture identity и payload по committed generator, затем обновляет check
только совпавших записей. Это проверка тестового источника, не real crawl и не
продление freshness от одного пересоздания proof.

Показывается только проверенная часть, с постоянным предупреждением о неполноте.
Подтверждённый ноль означает отсутствие совпадений в этой части, не во всём рынке.
Если нет ни одной пригодной проверенной записи, новая операция завершается
`SOURCE_COVERAGE_UNAVAILABLE` без списания. При частичном покрытии поиск, включая
ноль совпадений, успешен и стоит одну операцию. Обычные фильтры доступны отдельно.
Replay сохраняет исторический receipt/count; карточки перепроверяются, а истечение
сессии/results не отменяет уже подтверждённое списание и не запускает inference.

## 4. Сессии, восстановление и технические пределы

- Квота: guest 3 / auth 200 успешных операций за день Europe/Madrid по PostgreSQL,
  включая DST. Списание одно; reservation сохраняет исходный день через полночь.
- Guest identity: 7 суток от выдачи без sliding renewal. Secure/HttpOnly/SameSite
  Strict, host-only и AI path. Новая identity выдаётся явным bootstrap; invalid
  cookie в операции не заменяется молча. Ключ подписи независимый; поддерживаются
  до двух предыдущих verification keys. Кража/компрометация требует отзыва.
- Не более 3 активных диалогов на subject. Reset закрывает старый и создаёт новый;
  keyed create/reset переживает потерянный ответ. Login/logout меняет identity,
  не переносит guest criteria или квоту.
- HTTP body ≤32768 bytes, текст ограничен схемой. Общий HTTP deadline 20 с,
  execution 15 с. Lease reserved/running/grace: 60/60/30 с в lab.
- Распределённые Redis gates, без memory fallback: HTTP 120/мин/IP,
  чтение 60/мин/subject, выдача guest 2/мин и 10/час/IP, создание/reset 6/мин/subject,
  новые попытки 6/мин/subject и 30/мин/IP. Inflight: 4 глобально, 1/subject;
  токены истекают через 30 с и освобождаются только своим владельцем.
- `reserved/running`: повторять точный operation key+payload, не запускать второй
  inference. `succeeded`: вернуть исходный receipt; `failed`: terminal key не
  переоткрывается. Новый изменённый запрос требует нового явного действия.
- Minimal owned operation-status endpoint не возвращает fingerprint, criteria,
  lease fence или чужую запись. При неопределённом commit не выдумывать результат;
  recovery и повтор читают durable состояние. Отмена ожидания не доказывает rollback.

## 5. Уточнения и неоднозначности

Не угадывать период бюджета, rental mode, неоднозначный balcony/location/dates
или неподдерживаемое условие. Typed clarification с фиксированным reason завершается
без CAS изменения intent и без списания. Повтор показывает тот же вопрос без
provider call; ответ — новый operation key на той же версии. Опциональный
clarification key привязан к owner/session/version предыдущего вопроса.

Закрытый DeepSeek eval отдельно возвращает clarification/no_change/unsupported:
эти исходы отображаются фиксированным сообщением и не становятся частичным patch.
Текущий синтетический browser parser остаётся конечным набором тестовых фраз,
он не является произвольным real-user LLM. История, неуказанные условия и hard
ограничения сохраняются; ослаблять hard до soft без явного запроса нельзя.
