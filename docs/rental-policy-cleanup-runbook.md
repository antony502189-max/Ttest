# Long-term rental policy maintenance

Policy: `long-eur-month-1000-v1`. The admission limit is inclusive: verified exact EUR/month rent plus fixed mandatory monthly charges must be positive and at most 1,000 EUR. Deposits are separate. Historical holiday enum/schema remain readable for rollback.

## Review and authorization

No deployment, startup, migration, or importer calls this command. Production apply requires separate human approval of the enumerated JSON manifest, action and SHA-256 digest. Default action is withdrawal. Purge is an optional explicit action; any provenance, favorite, message, report, payment/promotion, notification, restriction, or unknown dependency makes a row ineligible for hard deletion and falls back to withdrawal.

Dry-run uses a read-only repeatable-read transaction. It lists every invalid nondeleted row and selects at most 500 actionable IDs per reviewed plan. It includes actual FK topology and cascading dependencies, per-source/status/city counts, canonical row hashes, relation hashes and attached media metadata hashes. It contains no contacts, message contents, account details, or storage keys. Keep the full manifest private; review exact IDs locally. Aggregate summaries are safe to share.

## Operator sequence (production execution not authorized by this PR)

1. Deploy approved code through the existing immutable release procedure. Keep `EXTERNAL_IMPORT_POLICY_VERSION` empty until rollout approval; the production worker must fail closed. Public eligibility guards immediately hide invalid legacy records.
2. In an approved maintenance window, stop all application writers (backend, mail worker, external worker and other jobs), preserve PostgreSQL/Redis/MinIO infrastructure, and prevent out-of-band DB writers. Do not stop production from an unapproved assistant session.
3. Create a private directory `$ROOT/shared/rental-policy` with mode 700. Run `python -m app.commands.enforce_long_term_price_policy --output /private/manifest.json` in the backend environment. Optional `--action purge --plan-limit 500` explicitly selects purge; defaults are withdrawal and dry-run. In the container mount the private directory at the same absolute path. Do not add `--apply`.
4. Review all candidates, exclusions, totals, assumptions and selected IDs. Obtain human approval for this exact digest and `WITHDRAW` or `PURGE` action. If anything changes, regenerate and review the manifest.
5. After the manifest, run existing encrypted PostgreSQL and MinIO backups and restore drills. Backups must be authenticated, less than 72 hours old and restore receipts less than six hours old. Set `RECOVERY_RECEIPT=$ROOT/shared/rental-policy/postgres-<unique>.json` for `deploy/restore-verify.sh <dump.enc>` and a different MinIO receipt for `deploy/restore-minio-verify.sh <archive.tar.enc>`. Each script retains the existing release lock and writes a private authenticated receipt only after successful restoration into disposable destinations. Receipts cannot be overwritten. The drills drop only their own temporary DB/bucket.
6. A separately authorized operator runs `deploy/apply-rental-policy.sh <manifest> WITHDRAW:<digest> <postgres-receipt> <minio-receipt>` (or `PURGE:<digest>` for an approved purge plan). The wrapper acquires the same release lock, checks authentication, rejects running application services and mounts backups read-only. The command rechecks backup bytes and all catalog/dependency/media hashes under table locks before making a bounded atomic transaction. A concurrent repricing/reference addition causes refusal and rollback.
7. Read the private apply result, rerun dry-run, verify public card/detail/map/favorite/media projections, and compare eligible €1,000 records before/after. If more than 500 candidates require writes, each next batch needs a new reviewed manifest, confirmation and restore proofs. No object-storage deletion occurs; shared assets and recoverable media remain.
8. Only after explicit rollout approval, set `EXTERNAL_IMPORT_POLICY_VERSION=long-eur-month-1000-v1`, start the approved worker and confirm rejection counters, stable source identities, worker heartbeat, error rate and latency. Resume application services through the normal approved procedure.

## Recovery

A failed transaction rolls back all writes. For a committed withdrawal, restore only reviewed listing status fields from the authenticated PostgreSQL backup into a temporary DB and compare IDs/hashes before an approved recovery; reverting public guards would expose invalid inventory. For committed purge, use the existing authenticated whole-database restore/runbook under the release lock, with all writers stopped, and the matching MinIO snapshot when needed. Preserve all backups, manifests and audit entries. No blind bulk restore, original-dump overwrite, shared asset deletion or automatic production restart is implemented.

Local tests cover inclusive prices and mandatory costs, read-only inventory, bounded plans, protected relationships, exact confirmation, timestamp tampering, changed dependencies, idempotence, transaction rollback and an opt-in actual pg_dump/pg_restore round trip of the pre-purge snapshot. Synthetic gate receipts in unit/integration tests are explicitly not production recovery proof. Production PostgreSQL and MinIO restore drills and actual production counts remain operator prerequisites.
