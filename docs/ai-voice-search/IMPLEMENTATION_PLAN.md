# Ttest / 112233.es — рабочий план AI-поиска и обогащения каталога

> **Статус:** рабочий документ / backlog, НЕ утверждённое заказчиком ТЗ.  
> **Создано:** 2026-10-24. **Ветка:** `planning/ai-voice-search-architecture`.  
> **Область текущего этапа:** парсеры, модель данных, AI-обогащение, качество импортированных объявлений.  
> **Следующий этап:** выбор AI API, контракт пользовательского голосового поиска, UX, ранжирование — после обсуждения и ответов заказчика.  
> **Важно:** этот документ фиксирует предложения, а не подтверждает их реализацию. Ниже все задачи по умолчанию НЕ выполнены.

## 0. Цель и границы

Подготовить импортированные и собственные объявления для поиска по естественной речи: состав проживающих (один/пара/друзья/семья), вместимость, дети, животные (с ограничениями), курение, место, бюджет, amenities и иные явно заявленные критерии. Пользовательский поиск должен обращаться к **локально сохранённым, достоверным и структурированным данным**, а не открывать сторонние сайты во время каждого запроса.

**Решения, которые можно принимать независимо от заказчика:**
- Использовать существующий импортёр; **не переписывать его с нуля**.
- Встроить дополнительный *асинхронный* этап извлечения фактов после принятия/сохранения объявления.
- Внешний LLM использовать для анализа текста по API; вычислительные модели локально на VPS не разворачивать.
- Хранить происхождение и доказательство каждого факта; отсутствие сведений != запрет.
- Раздельно учитывать источник, canonical-объявление и поисковое представление.
- Не блокировать публикацию/синхронизацию из-за отказа LLM.
- Переобрабатывать только новые/изменённые данные либо записи устаревшей версии схемы.
- Никакого браузерного агента на пользовательском запросе; повторное получение страницы — только разрешённым существующим адаптером и при необходимости.

**Пока не решаем:** конкретный API/провайдер/модель и тариф, эндпоинты, внешний JSON-контракт, весовые коэффициенты и пороги scoring, рекламное ранжирование TOP, интерфейс микрофона, хранение диалогов/аудио, оповещения. Они будут уточняться отдельно.

## 1. Подтверждённая база в репозитории (на момент написания)

| Участок | Фактическое состояние | Значение для плана |
|---|---|---|
| `backend/app/external_sources.py` | `ExternalListingSource`, `public_detail_fields()`, `NormalizedListing`; извлечение optional-полей регулярными выражениями/словарём | Расширяем сбор исходных фактов и сохраняем отсутствие значения как unknown |
| `backend/app/services/external_import.py` | `run_source()` → `parse_listing()` → `normalize_listing()` → `upsert()` | Здесь интеграционная точка **после сохранения**, без сетевого LLM внутри транзакции |
| `backend/app/workers/external_listings.py` | Уже работает отдельный импортёр с distributed lock / source health | Новый AI-worker должен быть отдельным и не мешать существующему |
| `backend/app/models/__init__.py` | `Listing`, `ExternalListingSource`; `raw_payload` и `normalized_payload` — JSONB; записи источника ссылаются на canonical listing | Можно строить versioned AI-факты по source record |
| `backend/app/models/room_details.py` | `ListingRoomDetails` с `room_capacity_v2`, `couples_allowed`, `accepted_tenant_types` и др. | Сверять полученные признаки с существующей моделью комнат |
| `backend/app/repositories/listings.py` | `apply_search_filters()`; `roomCapacity` сейчас фильтруется на **точное равенство**, а не `>=` | Не использовать эту семантику для будущего поиска «поместятся N человек» без отдельного решения |
| `docs/external-import.md` | Описаны правила допустимого импорта, дедупликации, геолокации, статусов и отсутствие обхода блокировок | Все ограничения сохраняем |
| `docs/spain-scale-architecture.md` | Серверный ограниченный карточный поиск; важные инварианты каталога, карты, TOP и геофильтров | Не переносить AI-ранжирование в импортёр; планировать совместимость с текущим поиском |

**Уже выявленные риски:**
1. В модели `Listing` ряд nullable полей имеет default, например `pets_allowed=False`, `children_allowed=False`, `smoking_allowed=False`, `room_capacity=1`, `bathroom="Baño compartido"`, `furnished=True`. Значение в существующем объекте **само по себе не доказывает**, что оно явно присутствовало в источнике. Не выполнять массовую «очистку» столбцов без отдельной миграционной стратегии и аудита.
2. `public_detail_fields()` распознаёт ограниченный набор фраз (включая испанские формулировки для курения/животных/детей). Реальные описания сложнее: отрицания, условия, смешанные языки и уточнения («маленькие животные», «курить только на террасе»).
3. `NormalizedListing.fingerprint` не включает все отдельные извлечённые условия (в т.ч. ряд optional boolean). Для AI-подсистемы нужен **независимый хеш полного релевантного текста/снимка + версия извлекателя**; не менять существующий fingerprint импорта без отдельного регрессионного плана.
4. `raw_payload` неоднороден: адаптеры иногда сохраняют краткую структуру, а не полный HTML; нельзя предполагать, что вся страница доступна в БД. Однако `Listing.description` и source normalized snapshots уже дают основу для backfill.
5. Один canonical listing может ссылаться на несколько источников; данные и даже ограничения могут противоречить друг другу. Нельзя писать результат LLM последнего источника поверх предыдущего без согласования.
6. Геолокация импортированной записи может быть приближённой или отсутствовать. Запрещено выдавать это за точный адрес или обещать время пешком без проверенных маршрутных данных.
7. Текущий каталог и платные TOP-объявления имеют собственные коммерческие и жизненные инварианты. AI-этап не должен их затрагивать.

## 2. Целевая схема потоков

```text
[разрешённая публичная страница источника]
        ↓
existing ExternalListingSource fetch / parse / normalize
        ↓
existing upsert → external_listing_sources + listings
        ↓ (после успешного COMMIT; событие или плановый scanner)
durable AI enrichment queue (PostgreSQL)
        ↓
dedicated enrichment worker
        ↓
normalize evidence input → external LLM API → strict schema validation
        ↓
listing_ai_facts (факты по source record, с доказательствами)
        ↓
canonical feature resolver (конфликты / приоритеты / неизвестно)
        ↓
listing_search_features (подготовленные признаки по listing_id)
        ↓
[будущий пользовательский AI-поиск через локальную БД]
```

Не выполнять:
- вызов LLM в `upsert()` или транзакции БД;
- полный повторный crawl при пользовательском поиске;
- LLM-SQL / произвольный URL-browser tool;
- автоматическое превращение «неизвестно» в «можно» или «нельзя»;
- отправку персональных контактов рекламодателей в LLM.

## 3. Backlog: текущая область — парсеры и хранение критериев

### P0 — аудит реальных данных до изменений

- [ ] **PARSER-001 / read-only аудит источников.** На тестовой/анонимизированной копии собрать репрезентативную выборку 50–100 принятых объявлений по каждому доступному источнику с учётом фактического количества, либо объяснить, почему меньше. Не запускать массовое повторное скачивание для аудита.
- [ ] **PARSER-002 / матрица полноты.** Для каждого источника измерить: % непустых `title`/`description`, длину описаний, доступные структурные поля, % unknown по животным/курению/детям/вместимости/парам/удобствам, долю записей с подтверждённой и примерной геопозицией.
- [ ] **PARSER-003 / инвентаризация потерь.** Проверить, где исходный публичный текст был доступен в `parse_listing()`, но терялся при `normalize_listing()`/`upsert()` или переопределении `description`. Составить per-source action list.
- [ ] **PARSER-004 / gold dataset.** Сформировать размеченный набор реальных (обезличенных) описаний: утверждение/запрет/отсутствует/условно/противоречие. Включить испанский, английский, русский, неявные отрицания и разные формы написания; сохранить исходный короткий evidence span и ожидаемый результат.
- [ ] **PARSER-005 / текущая семантика default.** Проверить legacy/imported записи и маппинг `Listing`: где `False`, `True` или `1` пришли из источника, а где могли быть подставлены. Зафиксировать, каким столбцам нельзя доверять как доказательству.

**Выход P0:** сводный отчёт по источникам + список исправлений, до выбора конкретной LLM.

### P1 — схема данных с сохранением происхождения

- [ ] **DATA-001 / модель фактов.** Добавить отдельное versioned хранилище `listing_ai_facts` (название предварительное): `source_record_id`, `canonical_listing_id`, `input_hash`, `schema_version`, `extractor_version`, `provider/model`, `facts_jsonb`, `created_at`, `status/error`, `processed_at`. Гарантировать уникальность обработки по source record + hash + schema version; продумать индексы.
- [ ] **DATA-002 / provenance.** Каждый распознанный факт должен хранить: `field`, нормализованное `value`, `status` (`explicit_true / explicit_false / conditional / unknown / conflict` либо эквивалент), короткий `evidence`, `evidence_source` (`description/structured/title`), исходный source record и момент последней проверки. Confidence не считать доказательством.
- [ ] **DATA-003 / каноническая проекция.** Добавить `listing_search_features` (название предварительное) по `listing_id`: агрегированные типизированные признаки/статусы для быстрого SQL-поиска, версия расчёта, метка свежести, информация о конфликте. Не читать source-facts и не вызывать LLM на каждую пользовательскую выдачу.
- [ ] **DATA-004 / tri-state и ограничения.** Отдельно различать `true`, `false`, `unknown`, `conditional` и `conflict` там, где они существенны. Например: `pets_allowed=true` + `species=dog` + `max_size=small` не эквивалентно безусловному разрешению всех животных.
- [ ] **DATA-005 / существующие объявления.** Для owner-created listings определить происхождение фактов: явный выбор владельца в форме, текст описания, legacy default, ручная правка. Указанное собственником не перетирать LLM-выводом.
- [ ] **DATA-006 / безопасность миграций.** Alembic **expand-only** на первом релизе; ни массовой перезаписи `listings`, ни удаления полей/старых индексов. Rollback через feature flag/выключение worker, сохранение старых данных.
- [ ] **DATA-007 / lifecycle.** При статусах `closed/deleted/hidden` не включать карточку в будущий AI-поиск; при promotion/смене primary source пересчитать канонические признаки без повторного LLM-запроса, если source-facts актуальны.

### P2 — усиление существующих source adapters

- [ ] **PARSER-006 / единый evidence input.** Стандартизировать **минимальный очищенный пакет** `title`, `description`, `category`, `breadcrumbs`, структурные provider facts и language/source metadata. Контактные телефоны, email, имена, HTML-код аналитики и произвольный page chrome исключать.
- [ ] **PARSER-007 / полнота описания.** Исправить per-source адаптеры только там, где P0 показал потерю доступного описания; предпочесть публичный JSON-LD/embedded data или серверный текст; браузер Playwright — fallback в рамках существующих разрешённых адаптеров, не универсальный agent.
- [ ] **PARSER-008 / извлечение условий.** Сохранить детерминированные извлечения для простых доказуемых полей; расширить словарь/покрытие только по тестовым кейсам. LLM используется как дополнительный, а не единственный способ извлечения.
- [ ] **PARSER-009 / не придумывать данные.** Не угадывать пол жильца, совместимость пары, отсутствие детей/животных, точный адрес, время в пути, площадь, вместимость и разрешения на основании молчания источника или фотографии.
- [ ] **PARSER-010 / отдельный digest.** Вычислять стабильный `ai_input_hash` из нормализованного значимого текста и структурных evidence-полей, а не полагаться на текущий import fingerprint. Изменение только телефона или порядка фото не должно запускать лишний LLM-анализ; изменение условий/описания должно.
- [ ] **PARSER-011 / fidelity и тесты.** Для каждого изменённого адаптера обновить HTML/JSON fixture tests; не ломать цену, категорию rental, географию, валидность gallery, source identity и дедупликацию.
- [ ] **PARSER-012 / отсутствие описания.** Когда значимого текста нет, сохранять причину `insufficient_source_data`, не генерировать галлюцинаторные факты; разрешённый повторный detail-fetch выполнять только по обоснованной фоновой задаче.

### P3 — слой AI-обогащения (не пользовательский API)

- [ ] **AI-ENRICH-001 / чистый сервис.** Вынести извлечение в независимый модуль, принимающий sanitized evidence input и возвращающий строго описанные факты. Никаких моделей/браузера в FastAPI request worker для каталога.
- [ ] **AI-ENRICH-002 / валидация.** Pydantic/schema, пределы длин, типы, допустимые enum/ranges, контроль, что evidence реально присутствует во входном тексте (или указывает на конкретное структурное поле). При отсутствии доказательства — unknown/на повторную проверку.
- [ ] **AI-ENRICH-003 / язык и отрицания.** Испанский, английский и смешанные тексты; «не курю» ≠ «в доме запрещено курить», «no se admiten parejas» ≠ «только один человек» при отсутствии дополнительного подтверждения, «perros pequeños» ≠ «любые питомцы».
- [ ] **AI-ENRICH-004 / конфликт нормализатора и LLM.** Явное структурное поле источника и проверенный текст должны сопоставляться; при противоречии не выбирать silently. Оставлять запись для инспекции и разрешения по правилам provenance.
- [ ] **AI-ENRICH-005 / версионирование.** Версия prompt, LLM, схемы, нормализатора и дата выполнения; возможность повторной обработки выбранной партии и сравнения с прошлой версией. Провайдер/модель выбираются позже.
- [ ] **AI-ENRICH-006 / защита входа.** Текст стороннего объявления считать недоверенными данными (prompt injection): не исполнять инструкции из объявления, не предоставлять LLM tools/SQL/секреты, запретить выполнение действий по содержимому.
- [ ] **AI-ENRICH-007 / методика проверки.** Сопоставить baseline regex и LLM на размеченной выборке; отдельно измерять опасные ложноположительные разрешения (например, «с собакой можно», когда запрет/неизвестно). Порог допуска определить по результатам пилота.

### P4 — очередь и отдельный worker

- [ ] **WORKER-001 / durable queue.** Таблица задач PostgreSQL (либо эквивалент с гарантированным восстановлением), idempotency key `source_record_id + ai_input_hash + schema_version`. Статусы `pending/running/succeeded/failed/dead_letter`; retry с экспоненциальной задержкой и jitter.
- [ ] **WORKER-002 / публикация событий.** После успешного commit import/upsert ставить задачу только при наличии нового digest/старой версии извлекателя; надёжность обеспечивать transactionally записываемой задачей/outbox либо периодическим reconciler; НЕ делать синхронный LLM-запрос.
- [ ] **WORKER-003 / ограничения.** Независимые concurrency/rate limits, budget cap (день/месяц), тайм-ауты, breaker при сбоях LLM; не конкурировать с importer за чрезмерное число соединений.
- [ ] **WORKER-004 / stale result protection.** После получения LLM ответа заново проверить `input_hash`/версию текущего source snapshot; результат устаревшего задания не должен стать активным.
- [ ] **WORKER-005 / отказоустойчивость.** Падение/недоступность AI-провайдера не блокирует публикацию и не закрывает объявления, не обнуляет прежние достоверные факты и не вызывает повторного скачивания сайта.
- [ ] **WORKER-006 / observability.** Метрики backlog, processed/s, p50/p95 latency, retry/dead-letter, estimated tokens/cost, % unknown/conflict, source coverage, freshness; structured logging без исходных персональных данных/секретов.

### P5 — обработка уже существующего каталога

- [ ] **BACKFILL-001 / dry run.** Без повторного crawling собрать admissible snapshot из `listings` + `external_listing_sources`. Зафиксировать число кандидатов и ожидаемую цену AI-обработки.
- [ ] **BACKFILL-002 / партиями.** Запустить идемпотентный backfill в тестовой среде; после подтверждения — контролируемые небольшие партии с паузой/остановкой. Приоритет: активные опубликованные карточки с непустым описанием.
- [ ] **BACKFILL-003 / пропуски.** Старые записи с пустым/плохим описанием не отправлять на «угадывание»; сформировать список источников для P2 исправлений или допустимого следующего refresh.
- [ ] **BACKFILL-004 / сравнение.** Замерить прирост доли подтверждённых фактов, % конфликтов, false positive и стоимость, до включения нового поиска.

### P6 — материализация и дальнейшая готовность к поиску

- [ ] **SEARCH-DATA-001 / resolver.** Разрешать source-level факты в canonical search features с учётом достоверности, актуальности, собственных явных полей, первичного/дублированных источников и конфликтов. Правила приоритета документировать и тестировать.
- [ ] **SEARCH-DATA-002 / вместимость.** Хранить подтверждённую максимальную вместимость отдельно от числа живущих сейчас и от дефолтных legacy-значений. Будущий смысл «поместятся N» — `capacity >= N`, а не текущий exact-filter.
- [ ] **SEARCH-DATA-003 / совместимость.** Раздельно моделировать `max_occupants`, `couples_allowed`, `children_allowed`, `pets restrictions`, `smoking indoors/outdoors`, `tenant restrictions`. «Сам пользователь не курит» — свойство его запроса, **не автоматический запрос жилья с полным запретом курения**.
- [ ] **SEARCH-DATA-004 / текст и гео.** Сохранять text-search evidence, тип/точность координат и неполноту; не объявлять «15 минут пешком» без маршрутизации. `listings.status`/visibility/price invariants продолжают контролироваться действующим backend.
- [ ] **SEARCH-DATA-005 / производительность.** Индексы и ограниченная выборка кандидатов; не вычислять join/aggregate всех source facts во время каждого пользовательского поиска. Проверка `EXPLAIN` на копии данных; без обязательной отдельной vector DB на MVP.
- [ ] **SEARCH-DATA-006 / рекламные места.** Сохранить существующую коммерческую логику TOP до отдельного решения по пользовательскому AI-ранжированию; не менять её как побочный эффект парсерных PR.

### P7 — безопасность, тестирование, выкладка

- [ ] **QA-001.** Юнит-тесты отрицаний, смешанных языков, условий/ограничений, неполного описания, conflicting sources, неизвестных значений и provenance.
- [ ] **QA-002.** Интеграционные тесты importer → commit → queue → worker → AI facts → canonical features; retry и restart; старый hash; promotion альтернативного источника; удаление/закрытие и status visibility.
- [ ] **QA-003.** Регрессии существующих адаптеров, дедупликации, gallery, pricing (long-term 1–1000 EUR), holiday mode, source health, блокировки и защита от ложного массового удаления.

## 4. Предлагаемый контракт данных об объявлении (внутренний пример, НЕ публичное API)

**Пример интерпретации доказанного ограничения источника:**

```json
{
  "source_record_id": "uuid",
  "schema_version": "v1",
  "facts": {
    "max_occupants": {
      "value": 1,
      "status": "explicit",
      "evidence": "para una persona"
    },
    "couples_allowed": {

    },
    "pets": {
      "allowed": true,

      "evidence": "Mascotas pequeñas permitidas"
    },
```

## 7. Критерии готовности этапа парсеров

## 9. AI API — предварительная архитектура и план проверки (2026-10-24)

> **СТАТУС: кандидаты / исследование, НЕ финальный контракт и НЕ решение заказчика.** Сначала проверить качество на реальных примерах и финансовые/юридические ограничения. Никаких API-ключей в репозитории.

### 9.1. Разделить на два самостоятельных контура

**Контур каталога — асинхронный, не пользовательский:**

```text
existing parser → normalize + commit → durable queue
→ AI enrichment worker → structured LLM extraction → schema + evidence validation
→ source facts → canonical resolver → search features in PostgreSQL
```

**Контур пользователя — синхронный по запросу, без посещения сайтов:**

```text
React MediaRecorder (или обычный текст)
→ Ttest FastAPI backend (API keys только на сервере)
→ speech transcription provider (только для аудио)
→ structured intent LLM
→ Pydantic validation & hard/soft constraints
→ PostgreSQL/PostGIS candidate filtering
→ deterministic compatibility ranking and existing visibility rules
→ cards + explanation/unknown conditions (если утверждено заказчиком)
```

Frontend не вызывает платные provider API напрямую и не получает их ключи. Не отправлять весь каталог в LLM. Не допускать произвольного выполнения SQL из ответа LLM. Персистентность диалога, уточнения и UI-формат — после ответов заказчика.

### 9.2. Проверенные API-кандидаты (официальная документация, 2026-10-24)

| Назначение | Кандидат | Факты из документации | Оценка / открытый вопрос |
|---|---|---|---|

### 9.3. Минимальные внутренние интерфейсы сервисов — без публичного URL-контракта

- `TranscriptionProvider.transcribe(audio, language_hints, vocabulary_hints) -> transcript + metadata`
- `IntentExtractor.parse(query_text, optional_current_filters) -> validated_search_intent`
- `ListingFactExtractor.extract(evidence_input, extractor_version) -> fact_set`
- `ListingFeatureResolver.materialize(canonical_listing_id) -> search_features`
- `CandidateMatcher.match(search_intent, pagination) -> matching_cards`

Это логические Python-интерфейсы; названия предложены для планирования, не являются кодом. API URL/версии схем/методы HTTP обсуждаются позже.

### 9.4. Операционная схема API

- **Timeouts:** раздельные тайм-ауты транскрипции, intent и фонового extraction. Общий пользовательский deadline + понятные ошибки; при сбое транскрипции разрешить текстовый ввод, при сбое intent сохранить обычный поиск доступным.
- **Retries:** 429/5xx — ограниченное количество попыток с jitter/Retry-After; не дублировать денежные запросы при клиентском повторном нажатии. Фоновые задачи идемпотентны.
- **Limits:** rate limiting по IP/сессии для анонимных пользователей, лимит длительности и байтов аудио, валидация MIME/контента. Учитывать provider quota на аудиосекунды, не только RPS.
- **Payloads:** аудио держать в памяти/короткоживущем temp-storage только до завершения обработки; исключить аудио и личные данные из обычных логов; политика сроков хранения и правовое основание требуют review.
- **Sessions:** хранить только нужное для последующего уточнения состояние фильтров в рамках пользовательской сессии; **не считать**, что DeepSeek хранит диалог: Responses API задокументирован как stateless. Полноценный чат и долговременное хранение — решит заказчик.
- **Search:** SQLite/локальную память каталога и отдельную векторную базу не добавлять; использовать текущий PostgreSQL/PostGIS с подготовленными признаками. Не нарушать существующие видимость, рекламные TOP, карту, стоимость и закрытые listings.
- **Deployment prerequisites:** перед активацией микрофона проверить и поправить `Permissions-Policy` в `backend/app/main.py` и `deploy/nginx.conf`, где сейчас отключён microphone; отдельный защищённый multipart endpoint потребует scoped body limit вместо обычных ~256 KiB. Это будущая задача, не изменение текущего PR.
